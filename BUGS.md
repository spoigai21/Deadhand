# BUGS — what broke, what caught it, the fix

| # | Phase | What broke | What caught it | Fix |
|---|---|---|---|---|
| 1 | 1 | OSRM's `table` call returned a road distance of **−0.1 m and −0.2 m** (duration 0) for two candidate legs whose driver and pickup both snapped to the same point on 7th Avenue, 107 m from the pickup's recorded coordinates. The straight-line distance was 104 m, so the ratio came out negative. | `tests/test_phase1.py::test_distance_sanity_haversine_never_exceeds_road`, the "road time is never negative" rule from `SPEC.md`, on the first full run. Two rows in 1.5 million. | Pairs whose road distance is under 1 m are excluded and counted as `same_road_point` in the results file. The sign of the number was the symptom; the cause is two endpoints collapsing to one road node, which says nothing about the matcher. **Phase 2 hit it again** through the oracle's table call (`test_no_double_match` asserts every leg is non-negative); the oracle now clamps a negative road distance or time at zero. The calibration ledgers run before the clamp were discarded; their run summaries (match rate, wait) are unaffected to the stated precision. |
| 2 | 2 | A calibration replay (7,500 drivers) died 70% of the way through the day: OSRM answered one `table` call with an empty body, the client tried to parse it as JSON and the oracle crashed, losing the run. Three other replays were hitting the same container at the time. | The run's log; the results file never appeared. | The routing client retries a call up to five times on a dropped connection or a non-JSON reply, with a short backoff. A replay that cannot reach OSRM five times in a row still stops, loudly. |
| 3 | 3 | The cruise demand map read the **same day's 23:00 hour as well as the previous day's** for drivers cruising between midnight and 01:00: the map was built over a window from one hour before midnight to the end of the day and keyed by hour of day only, so both 23:00 hours fell into one bucket. The `SPEC.md` rule is no lookahead. Hour 0 is the only hour affected; the other 23 read exactly the previous clock hour. | Exporting the demand map for the Java workers (`deadhead/phase3_data.py`), which had to spell out which day each hour came from. | The window now ends at 23:00 of the day, so hour 23 holds the previous day's pickups only. The Phase 2 ledgers were produced before the fix; it changes some cruise targets in the first hour of the day and nothing else, and the Phase 2 numbers are not re-run. The Phase 3 reference oracle and the workers both read the fixed map. |
| 4 | 3 | On a kept-alive HTTP connection the OSRM container answered a small `route` reply **43 ms** late (1.3 ms on a fresh connection; a 50-candidate `table` reply 3.8 ms against 3.0 ms). The Java worker's first full run spent 95% of its wall clock in cruise routing. The stall appeared after the container was recreated by `docker compose up`; the Phase 2 replays on the earlier container measured 1.1 ms per route with a kept-alive session. The 40 ms is the delayed-ACK timer of the Linux VM behind Docker's port proxy interacting with Nagle's algorithm on a one-segment reply. | The worker's per-stage wall-clock profile (`profile` in the worker summary): 6,704 route calls, 291 s. | Both routing clients (`deadhead/routing.py`, `consumer/.../Osrm.java`) send `Connection: close` and open a connection per call. The cost of a localhost connection is under the cost of the stall by a factor of thirty. The Phase 2 and Phase 3 routing-latency figures in `NUMBERS.md` are stated with the connection mode they were measured in. |
| 5 | 3 | The first full one-worker service run decided **382,318 of 391,042** requests. The worker's merge loop stopped reading a partition at its end-of-day marker while a fetched batch of that partition was still buffered, so 8,724 requests at the tail of the day were never decided. | The decided count against the oracle's ledger: every request has a decision in the oracle, and `missing_in_service` in `deadhead/phase3_metrics.py` was not zero. | The end-of-day offset is committed only once the partition's buffered records are drained (`eodOffset` in `Worker.java`). The run was voided and rerun; `missing_in_service` is 0 in every results file. |
| 6 | 3 | In the first kill dry run the surviving workers stalled **12–24 s** after the kill, twice the session timeout. Two causes. A dead peer's clock was dropped after a fixed 3 s, but a live worker inside a long cruise burst published no clock for longer than that, so live peers were expired and re-admitted; and a worker that had finished its partitions exited on its own, which caused rebalances the test did not intend. | The widest gap in decision completion times per partition around the kill (`stalls` in the kill metrics) and the workers' event lines. | A peer expires after two session timeouts or at the next rebalance; the clock is published inside the cruise loop; a worker stays in the group until the launcher stops it. |
| 7 | 3 | The first double-claim check, judged at the request's event time as the oracle's check is, reported **8–13 double claims** per kill run. None was one: a request the kill delayed is decided at a later wall-clock moment, after the driver's previous trip has ended, and compared by event time it overlaps that trip. | Reading the flagged pairs: every one was a delayed request whose driver was idle at the moment of the decision. | The check is judged at the time the decision was made (`now`), and the by-event-time count is reported beside it as `overlaps_by_request_time_explained_by_delay` so the two cannot be confused. |
